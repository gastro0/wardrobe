# Git, проверки и выпуск Forma Wardrobe

Основная ветка — `main`. Названия опубликованных окружений — **`test`** и **`prod`**.
Приложение и `autotests` находятся в одном Git-репозитории, но устанавливаются
как отдельные npm-проекты. Это позволяет менять код и связанные тесты одним PR.

## Обычная задача

На чистой рабочей папке обновите `main` и создайте ветку:

```powershell
git switch main
git pull --ff-only
git switch -c feat/outfit-favorites
```

Ветки: `feat/` — новая возможность, `fix/` — исправление, `chore/` — настройка,
`docs/` — документация. Название описывает задачу. На каждую самостоятельную
задачу открывается отдельный Pull Request в `main`.

Если изменения уже начаты в `main`, сначала проверьте `git status`, затем
создайте новую ветку через `git switch -c ...`: незакоммиченная работа останется
в рабочей папке. Перед `pull` разберите её, а не смешивайте с входящими изменениями.

После изменения кода проверьте приложение:

```powershell
npm.cmd ci
npm.cmd --prefix autotests ci
npm.cmd run typecheck
npm.cmd run lint
npm.cmd test
npm.cmd --prefix autotests run test:photo-alpha
npm.cmd run build
npm.cmd run test:photos -- --production-worker
# В другом терминале запустить npm.cmd start, затем:
npm.cmd run test:e2e
```

Перед коммитом просмотрите diff и добавляйте конкретные файлы или части файлов:

```powershell
git status --short
git diff
git add app/outfits-section.tsx autotests/e2e/wardrobe.test.mjs
git diff --cached
git commit -m "feat: добавить избранные образы"
git push -u origin feat/outfit-favorites
```

Пути и название в примере нужно заменить файлами своей задачи. `git add -p`
позволяет выбрать отдельные изменения в одном файле. Не включайте в коммит
несвязанные правки. Коммит — законченное изменение с понятным описанием;
префиксы `feat:`, `fix:`, `chore:` используются как соглашение проекта.

Откройте PR на GitHub: опишите результат, проверки, необходимые миграции и
настройки. Для незавершённой работы используйте Draft. После успешного CI и
проверки diff выполните **Squash and merge**, удалите завершённую ветку и
обновите локальную `main`. При работе одному PR проверяется самостоятельно;
обязательный второй ревьюер вводится при появлении второго участника.

## CI

`.github/workflows/ci.yml` проверяет PR в `main`, коммиты в `main` и начальную
ветку настройки `chore/git-ci-workflow`. Ветка настройки включена в запуск
явно, чтобы проверить первый pipeline ещё до слияния. Workflow можно также
запустить вручную через Actions после появления его в основной ветке.

Job `validate` устанавливает оба npm-проекта, проверяет типы, линтер, модульные
и серверные тесты, маску фото, сборку, собранный worker обработки фото и E2E.
Браузер устанавливается через CLI закреплённого `playwright-core`.

Проверки запускаются на Ubuntu с Node.js 22. Серверные тесты используют
временные D1/R2, E2E подменяют все `/api/`. Локальный Worker в CI сохраняет
состояние только в `autotests/.artifacts/worker-state`. CI не публикует приложение,
не применяет миграции к удалённым базам и не получает секреты `test` или `prod`.
При ошибке сохраняются диагностические файлы на 7 дней.

В GitHub для `main` нужно включить правило защиты:

- Require a pull request before merging; пока без обязательного второго reviewer.
- Require status checks to pass: `validate` после первого запуска CI.
- Require branches to be up to date before merging.
- Запрет force push и удаления ветки; применять ограничения и к администраторам.
- В настройках слияния использовать Squash merge.

Добавление workflow в Git не включает защиту ветки автоматически: это отдельная
настройка репозитория на GitHub.

## Окружения test и prod

`test` и `prod` — названия сред, а не дополнительные постоянные ветки.

| Среда | Назначение | Ресурсы |
| --- | --- | --- |
| local | Разработка и автоматические проверки | Локальные Worker/D1/R2, тестовые данные |
| test | Проверка настоящей интеграции перед выпуском | Отдельные Worker, D1, приватное хранилище фото и Telegram-бот |
| prod | Приложение пользователей | Рабочие Worker, D1, фотографии и основной бот |

Целевой порядок после подключения стендов: слияние в `main` → публикация в
`test` → проверка через тестового бота → ручной выпуск проверенного коммита в
`prod`. Успешный локальный CI не заменяет проверку реальных Telegram и Storage.

На первом этапе подключён CI. Публикация в `test`/`prod` будет подключаться после
создания тестовых ресурсов и настройки доступа к Cloudflare. Существующий
рабочий Worker, данные и настройки бота этот workflow не меняет.

При настройке CD окружения GitHub и Cloudflare называются `test` и `prod`.
У каждого свои переменные и секреты. Токены Telegram и ключи Storage хранятся
в секретах соответствующего Worker; CI-проверки PR не получают доступ к ним.
Токен Cloudflare для публикации хранится в GitHub Secrets с нужными правами.

Нужно устранить зависимость публикации от наличия локального
`wrangler.telegram.json`: pipeline должен получать однозначную конфигурацию
целевого окружения. При использовании Cloudflare Vite Plugin окружение
выбирается **до сборки** через `CLOUDFLARE_ENV=test` или `CLOUDFLARE_ENV=prod`.
Переменная на стадии deploy готового `dist` не переключает его ресурсы.
До подключения конфигурации окружений эти переменные не являются готовыми
командами публикации для текущего проекта.

В `prod` выпускается тот же исходный коммит, который успешно проверен на `test`.
Если `main` уже изменилась, выпуск не должен автоматически подменять его новым
коммитом. Релиз отмечается тегом, например `v0.2.0`, и записью SHA в журнале
публикаций. Одновременные публикации в одно окружение должны выполняться по очереди.

## Миграции и откат

Новые SQL-миграции добавляются в `drizzle/`; применённые файлы не редактируются.
Сначала миграция проверяется на временной базе в CI, затем на D1 среды `test`.
Применение к `prod` выполняется только в процессе согласованного релиза.
Изменения схемы должны сохранять совместимость с предыдущей версией Worker.

`git revert` создаёт новый коммит, отменяющий изменение без переписывания истории.
Возврат предыдущей версии Worker не отменяет миграции и не восстанавливает
удалённые данные: план восстановления базы готовится отдельно.
